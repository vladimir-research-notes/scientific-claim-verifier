A real Markdown report, reproduced verbatim, for the fixture this project exists for: a paper whose abstract asserts a number its own results table contradicts. ## 1. Extracted claim

The typed fields a rule-based extractor recovered from the claim sentence. Extraction is a
transparent heuristic — regular expressions and small closed lexicons, not a language model —
and an empty field means the extractor found nothing rather than that nothing is there. See

An empty field prints —, never None and never a guess. Extraction is a labelled heuristic, and conditions: — means the extractor found no condition, not that the claim has none.

§2 and §3 — supporting text, then the computed check

## 2. Supporting text (retrieved evidence)

The passages the evidence linker retrieved for this claim. Retrieval is not support: that a
passage was retrieved says nothing about whether it asserts the claim. Section 3 is where that
is checked.

> Method B reaches an F1 score of 91.0 on MNLI.

- passage p_claim · score 1.000 · match=declared_source_passage; overlap=1.000; rank=1

Other artifacts linked to this claim:

- table t_mnli [col=f1] · score 1.000 · match=table_column

## 3. Computed checks

Each check reads one artifact and records what it found. A check produces evidence; it does not
decide the claim's support label — that inference is section 4. A check's status is a fact about
the check; its signal is what the check says about the claim, and the two differ: an evidence
check that fails because the passage never mentions the claim refutes nothing. See
docs/CHECKS.md and docs/SCORING.md.

| Status | Check | Target | Computed | Expected | Tolerance | Signal |
| --- | --- | --- | --- | --- | --- | --- |
| pass | evidence_presence | p_claim | verbatim | — | — | supports |
| fail | table_value | t_mnli[col=f1] | 86.0 | 91.0 | 0.05 | refutes |

- c_contradicted_f1.evidence_presence.1 (pass → supports)
  check: the passage states the claim verbatim
  signal: the linked passage states the claim (verbatim)
- c_contradicted_f1.table_value.1 (fail → refutes)
  check: claimed 91 is absent from column 'f1' (nearest 86 at row B; |difference| = 5 > tolerance 0.05)
  signal: the table does not hold the claimed value

This is the whole design in eight lines. The abstract states the claim verbatim, so the evidence check passes. The results table reports 86.0, so the table check fails. Both are correct. A system that collapsed them into one verdict would report contradicted and throw away the fact that the paper asserts the claim in its own words — which is the finding.

Note also the two columns that would be one in a lesser tool: a check's status is a fact about the check, and its signal is what the check says about the claim. They are not the same question, and one status maps to more than one answer — an evidence check that fails because the passage never mentions the claim signals undecided, not refutes. Silence is not refutation.

§4 — the inference, with the rule that produced it

## 4. Inference

A verdict is not a summary of the checks; it is an inference from them. Each rule names itself
and the check ids it read, so the verdict can be re-derived without re-reading the code.

- support_label: contradicted
  rule: artifacts_refute [c_contradicted_f1.table_value.1]
  because: the table does not hold the claimed value
- reproduction_status: not_applicable
  rule: no_reproduction_channel [no checks]
  because: the claim references no script to run and no dataset to recompute from, so nothing
           here re-derives a number
- failure_mode: table_cell_mismatch
  rule: cause:table_cell_mismatch [c_contradicted_f1.table_value.1]
  because: the table does not hold the claimed value

confidence 1.00 — the share of this claim's checks that reached a pass/fail verdict. It is not a
probability that the label is correct, and it is not calibrated against anything.

Every inference names the rule that produced it and the check IDs that rule read. "Why does this claim say contradicted?" is answered by a lookup, not by re-reading the code. And confidence never appears without the sentence that says what it is not: it is decidedness, the share of checks that reached a verdict, and a claim whose only check is inconclusive scores 0.00 no matter how confident its label sounds.

## 6. Trace

This report was rendered from the trace below and from nothing else: no task file was read, no

[contradicted_f1.trace.jsonl](../runs/smoke_suite/contradicted_f1.trace.jsonl)

9 JSONL events, schema 1.3. Keys are sorted and nothing is read from the wall clock, so two runs
of one task produce byte-identical traces — including tasks whose fixture script actually
executes.

A report is a function of its trace

The report generator does not import the extractor, the linker, the checks, or the sandbox. It reads one <task_id>.trace.jsonl and reconstructs the scored claim from it — re-validating every object against the schema on the way in, so a corrupt trace raises rather than rendering into a plausible-looking report. A run archived months ago, whose papers and CSVs are long gone, still reports.

That is a claim worth testing rather than asserting, so a test scores every committed fixture, writes its trace, reads it back, and asserts the reconstruction equals the original result, rules, and signals. If a later milestone records a fact in the result but not in the trace, that test fails.

Milestone 9 changed the trace to make this possible, and bumped SCHEMA_VERSION to 1.3 to say so. A scoring.run event now opens the stream, naming the run, the task, the bundle, and the schema — facts that previously survived only in the filename — and scoring.claim carries the whole extracted claim rather than five of its fields. A pre-1.3 trace is refused by name, with an instruction, rather than guessed at.

The other ten

report renders every claim in a run, plus an index linking each report to its trace, in the suite's evidence-channel order. Two of the eleven are worth reading next to this one:

  • synthetic_data_passage — the report that decides nothing. Its passage does support the claim, but only by paraphrase, and a bag-of-words rule cannot see it. §4 reads unverifiable_from_artifacts, confidence 0.00, and §5 says exactly what could not be decided (40% token coverage, missing ['model', 'only', 'trained']). The word contradicted appears nowhere in it — a test asserts that. Reporting a contradiction there would publish the checker's ignorance as a fact about the paper.
  • unreproducible_accuracy — a complete, working script whose predictions.csv the paper never released. code_execution is error, numeric_tolerance is skipped (no number disagreed with 0.95, because no number exists), and §5 carries three limitations — including the one every sandboxed report carries whether or not its verdict was favourable: the script ran under a recorded policy in a temp directory, which is controlled fixture execution and not a security boundary.
Reports come in Markdown and, with --format html, as one standalone HTML file each — no stylesheet to ship beside it, no JavaScript, no network fetch. An audit artefact may be read years after the run, from a directory someone copied off a machine, so it must not depend on anything that directory does not contain. Both formats walk one document tree, so they cannot disagree about what the pipeline concluded. See Results and docs/REPORTS.md.
