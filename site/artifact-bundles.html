Artifact bundles

A task bundles the evidence a claim will be checked against: paper snippets, tables, figure metadata, datasets, code files, and expected outputs. Everything is small, synthetic or open, and content-hashed for provenance.

Task layout

Tasks are YAML/JSON under tasks/, grouped by family; their file-backed artifacts (datasets, code) live under data/fixtures/. Papers, tables, and gold expectations are inlined in the task file. See docs/ARTIFACT_FORMAT.md for the full task-file reference.

tasks/
  ml_claims/            bioinformatics_claims/    statistical_claims/
  table_claims/         code_reproduction/

data/fixtures/
  datasets/     code/

Input vs. gold

A task keeps the claim as authored (id, text, type, source) separate from the gold record of what the answer should be (the target extraction values, support label, reproduction status, and evidence links). The gold record scores later milestones; it is never fed to them as input, so loading a task cannot leak the answer to the extractor.

Provenance & hashing

Each PaperArtifact, DatasetArtifact, and CodeArtifact carries a content_hash field (typed in Milestone 1; populated by artifacts/hashing.py in Milestone 2). The loader hashes datasets and code over their file bytes and inlined papers over a canonical JSON of their passages, producing a deterministic sha256:<hexdigest>. The hash is recorded in the trace so a report can state exactly which bytes a verdict was computed against, and a re-run against changed artifacts is detectable.

Bundle integrity

The ArtifactBundle schema enforces, at construction, that artifact IDs are unique across papers/datasets/code and that table, figure, and passage IDs are unique within their scope. A duplicate is a hard validation error, so every EvidenceLink resolves to exactly one target — a precondition for auditable provenance.

Fixture rules: small, synthetic or open, committed. No private/real papers, no large datasets, no model weights. See Safety and the repository .gitignore.

Validation

claimverifier validate-fixtures and scripts/01_validate_fixtures.py validate every task under tasks/, accumulating all problems per task. Errors (which fail the run) include: a file that does not parse or fails the schema; a duplicate artifact/table/figure/passage ID; a dataset/code path that is absolute, escapes the repository, or is missing; a dataset whose declared columns/n_rows disagree with its CSV; and an evidence link or source passage that resolves to nothing. Warnings (which do not) flag fixtures outside data/fixtures/, a filename that does not match its task_id, or a reproducible claim with no expected value. The milestone runner invokes the script as a between-milestone guard. All six committed fixtures currently validate with zero errors and zero warnings.
