Verification checks

Checks are deterministic and transparent. Each takes a claim plus its linked artifacts and emits a VerificationCheck record with inputs, computed value, expected value, tolerance, pass/fail, and notes.

Before a check runs: evidence linking

A check cannot run until something has said where to look. That is the evidence linker (Milestone 4): it takes the extracted claim and the artifact bundle and emits scored EvidenceLink records, each with a locator precise enough for a check to read the value back.

A link retrieves evidence; it does not judge it. A passage can be linked with a high score and contradict the claim. A table column is linked precisely because no cell matched the claimed value — otherwise a contradicted verdict could never be reached. And a cell is linked only when the claim names its row: given "the method reaches 90% accuracy" against a table of dev 90.0 / test 82.0, the linker emits col=accuracy, not row=dev, so the underspecification stays visible instead of hiding inside a confident-looking locator. Deciding whether linked evidence asserts a claim is the evidence_presence check below.

The keyword baseline is bag-of-words: it has no model of negation, morphology, or synonymy, so "the model is not trained on synthetic data" scores identically to the assertion. That limitation is documented, tested, and is exactly why retrieval and judgement are separate stages. See docs/EVIDENCE_LINKING.md and Results.

Tolerance handling

Numeric comparisons never rely on exact float equality. Each numeric claim carries an expected value and an operator; the check applies an absolute or relative tolerance (defaulted per metric, overridable per task) and records both the raw difference and the tolerance used, so a near-miss reads as approximately reproduced rather than a hard fail. See Reproducibility.

Code execution

The code-execution check runs tiny, trusted fixture scripts through the sandbox layer: a temp working directory, a wall-clock timeout, captured stdout/stderr/exit-code, and a no-network policy. This is controlled fixture execution for reproducibility — not an untrusted-code or exploit sandbox, and it makes no production-grade isolation claim. See Limitations.

A check never decides the final label alone. Checks produce evidence; scoring maps the set of checks onto a support label, a reproducibility status, and (on failure) a failure mode.

Determinism

Checks avoid wall-clock and unseeded randomness in anything that affects their output. Ordering is stable, and every computed value is written to the JSONL trace so a report can be regenerated and audited without re-running the checks.
