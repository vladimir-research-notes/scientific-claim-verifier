Verification checks

Checks are deterministic and transparent. Each takes a claim plus its linked artifacts and emits a VerificationCheck record with inputs, computed value, expected value, tolerance, pass/fail, and notes.

Before a check runs: evidence linking

A check cannot run until something has said where to look. That is the evidence linker (Milestone 4): it takes the extracted claim and the artifact bundle and emits scored EvidenceLink records, each with a locator precise enough for a check to read the value back.

ChannelHow it resolvesLocator
PassageExact verbatim lookup, then a Dice keyword-overlap baseline over every passage.—
TableA column denoting a claim metric; a cell when the claim names the row.row=A,col=accuracy · col=accuracy
DatasetName resolution, then the sole non-identifier column (or the metric-named one).column=value
CodeA .py filename in the claim, else the bundle's sole script.stdout
FigureThe data series named after a claim metric.series=accuracy
A link retrieves evidence; it does not judge it. A passage can be linked with a high score and contradict the claim. A table column is linked precisely because no cell matched the claimed value — otherwise a contradicted verdict could never be reached. And a cell is linked only when the claim names its row: given "the method reaches 90% accuracy" against a table of dev 90.0 / test 82.0, the linker emits col=accuracy, not row=dev, so the underspecification stays visible instead of hiding inside a confident-looking locator. Deciding whether linked evidence asserts a claim is the evidence_presence check below.

The keyword baseline is bag-of-words: it has no model of negation, morphology, or synonymy, so "the model is not trained on synthetic data" scores identically to the assertion. That limitation is documented, tested, and is exactly why retrieval and judgement are separate stages. See docs/EVIDENCE_LINKING.md and Results.

Five outcomes, not two

A check that runs and finds the artifacts disagree says fail. A check that runs and whose method cannot decide says inconclusive — a distinct status, added to the schema in Milestone 5 (version 1.1, additive).

StatusMeaningSignal it reduces to (M7)
passThe artifacts agree with the claim.supports — or ambiguous, for a column lookup the claim never disambiguated
failThe artifacts disagree.refutes — except an absent passage, which decides nothing
inconclusiveThe method cannot decide.undecided → unverifiable_from_artifacts
errorThe check could not run.undecided → failed_* reproduction, via error_kind
skippedThe check did not apply.undecided — a limitation, not a failure
Without inconclusive, a transparent lexical check faced with a paraphrase would have to report fail, and scoring would manufacture a contradiction out of the checker's own ignorance. The distinction between "the artifacts say you are wrong" and "I cannot tell" is the difference between an auditable tool and a merely confident one.

A status is a fact about the check; the signal is what the check says about the claim, and the mapping is not one-to-one in either direction. Scoring reads only signals — see Reproducibility & scoring.

error_kind: why the check could not run

Every error check records a closed-vocabulary cause in inputs.error_kind: dangling_link, missing_passage, missing_data, unreadable_data, missing_code, sandbox_failure, execution_timeout, nonzero_exit, missing_column, missing_row, non_numeric_cell, empty_column. Scoring maps these onto reproduction statuses and failure modes with a table lookup — "the script is missing" and "the sandbox broke" are different outcomes, and distinguishing them by matching English in a notes field would not be a contract. The notes remain the human explanation; error_kind is the machine one.

Evidence presence: what a lexical check can and cannot confirm

The linker retrieves the passage; this check asks whether the passage says the claim. It reports one of five levels, and only two of them pass.

LevelRuleStatus
verbatimThe claim's canonicalized text occurs in the passage.pass
token_subsumedEvery content token of the claim occurs, polarity matching.pass
polarity_mismatchTokens all present, but the quoting sentence negates the claim.fail
partial_overlapSome claim tokens are missing.inconclusive
absentNo claim token occurs at all.fail

On the committed fixtures exactly one claim lands on partial_overlap, and it is exactly the one whose supporting passage is a genuine paraphrase: "the model is trained only on synthetic data" is supported by "no real corpora were used at any stage of training", and a bag-of-words rule cannot bridge trained to training. It says so instead of guessing. See Results.

Tolerance is read off the claim, not chosen

Numeric comparisons never rely on exact float equality. The default tolerance is the claim's own reported precision: half of the last decimal place of the number as it was written. So the tolerance is a property of how the claim was stated, not a constant tuned until the fixtures went green.

Claim textToleranceReasoning
a mean value of 3.4±0.05anything that rounds to 3.4
an accuracy of 0.80±0.005two decimals were reported
reaches 90% accuracy±0.5reported to the nearest integer
12 samples±0a count is exact

Overrides, in precedence order: --abs-tol/--rel-tol on the command line, then a tolerance: block in the task file, then the reported precision, then float noise. Every check records the threshold it actually applied alongside the signed difference. See Reproducibility.

Code execution

The code-execution check runs tiny, trusted fixture scripts committed to this repository, through the Milestone 6 sandbox: a fresh temp working directory, an environment scrubbed to an allowlist, closed stdin, POSIX resource limits applied before exec, a wall-clock timeout that kills the whole process group, and an in-process guard that makes socket calls raise and records them. The full policy is written into the run's trace, ahead of the number.

Those are reproducibility controls, not security controls: no process isolation, no namespace, no seccomp filter, and a network guard that lives inside the child's own interpreter. It is not a security boundary of any kind. See Limitations.

Two consequences reach the check. A script that reached for the network is not self-contained even if it printed the right number, so the denied calls land in the check's inputs and its notes. And if the sandbox could not enforce the policy it promised, the check is error — reporting the output anyway would attribute a number to conditions that never held. The artifact's declared entrypoint is recorded but never parsed or executed: a task file must not be able to name a command to run.

Execution failure is not numeric disagreement: a timeout or a non-zero exit is error, never fail, because a script that will not run tells you nothing about the claim's number. Whether the number it printed matches is a separate numeric_tolerance check — which is why failed_environment and failed_numeric_mismatch can be told apart in a report.

A check never decides the final label alone. Checks produce evidence; scoring maps the set of checks onto a support label, a reproducibility status, and (on failure) a failure mode — and names the rule it used. The contradicted_f1 fixture is the proof: the paper's abstract asserts the claim verbatim (evidence_presence passes) while its own results table refutes it (table_value fails). Both are true, the label is contradicted, and the report still shows the passage that asserts it. A single collapsed verdict would destroy that fact.

Determinism

Every check is a pure function of its inputs apart from code execution, which starts a child process. No wall clock, no RNG, and no absolute filesystem paths reach a check's recorded output: the command is recorded as ("python", "gc_content.py"), never the machine's interpreter path; the sandbox's random temp path is replaced with <sandbox> in captured output; and no duration is recorded (timing lives in the sandbox trace, where it is opt-in). The child runs with PYTHONHASHSEED=0 and TZ=UTC. Floats are rounded to 12 decimal places, so 40.8 / 12 is written 3.4 rather than 3.4000000000000004 — far below any tolerance in play, so rounding can never flip a verdict. Checks are emitted in a fixed type order with ids numbered per type.
