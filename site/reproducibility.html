Reproducibility & scoring

Scoring maps the set of checks onto three explicit vocabularies: a support label (is the claim backed?), a reproducibility status (did the computation reproduce?), and a failure mode (if not, why?).

Support labels

LabelMeaning
supportedChecks confirm the claim against the artifacts.
contradictedChecks show the artifacts disagree with the claim.
partially_supportedSome but not all of the claim holds (e.g. direction right, magnitude off).
underspecifiedThe claim omits conditions needed to check it unambiguously.
unverifiable_from_artifactsNo artifact in the bundle can settle the claim.
not_checkedNo applicable check ran.

Reproducibility statuses

StatusMeaning
reproducedRecomputation matches within tolerance.
approximately_reproducedMatches within a looser, recorded tolerance.
failed_environmentExecution failed for environment reasons.
failed_missing_dataRequired dataset artifact absent.
failed_missing_codeRequired code artifact absent.
failed_numeric_mismatchRan, but output is outside tolerance.
not_applicableClaim needs no computation (e.g. descriptive).
not_attemptedReproduction was possible but not run.

Failure modes

When a claim is not cleanly supported/reproduced, the result carries a failure_mode that names the reason: missing evidence link, passage does not assert the claim, table cell mismatch, statistic mismatch, numeric out of tolerance, missing data, missing code, execution error/timeout, or underspecification. Failure modes are what make aggregate results diagnostic rather than a single pass-rate number.

Aggregate summary

A suite run produces a summary (CSV/JSON) counting support labels, reproducibility statuses, and failure modes across tasks — see Results. Scoring is deterministic: explanation quality is judged by expected fields, not by an LLM grader.
