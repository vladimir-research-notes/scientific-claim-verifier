Reproducibility & scoring

Scoring maps the set of checks onto three explicit vocabularies: a support label (is the claim backed?), a reproducibility status (did the computation reproduce?), and a failure mode (if not, why?).

A check's status is not its meaning

Scoring never reads a check's status directly. It first reduces each check to what that check says about the claim — supports, refutes, ambiguous, or undecided — because one status means more than one thing:

CheckStatusSignalWhy
evidence_presencefailrefutesThe passage has the claim's tokens and negates them.
evidence_presencefailundecidedThe passage never mentions the claim. Silence is not refutation.
table_valuepasssupportsThe value is in the cell the claim named.
table_valuepassambiguousThe value appears somewhere in a column of several rows; the claim named none.
code_executionpasssupportsThe script printed the output the bundle declared.
code_executionpassundecidedNothing was declared. Exit 0 alone is not evidence for a number.

Support labels

Five ordered rules over the signals. The first to fire wins, and the report and the trace record which rule fired and which checks it read.

LabelRuleMeaning
contradictedartifacts_refuteSome check refutes the claim.
underspecifiedclaim_ambiguousNothing refutes it, but a check cannot tell which value the claim means.
supportedall_checks_supportEvery check reached a verdict, and all support the claim.
partially_supportedsome_checks_supportSome support it, some could not decide, none refute it.
unverifiable_from_artifactsnothing_decidedNo check reached a verdict.
not_checkedno_checksNo check ran at all (a guard).

Order is the argument. Refutation beats ambiguity: a value absent from a column is contradicted whether or not the claim also omitted the row. Ambiguity beats support: underspecified_split does find 90.0 in the accuracy column, and calling that supported is exactly the overclaim the label exists to prevent — the table reports 90.0 on dev and 82.0 on test, and the claim never says which.

nothing_decided maps to unverifiable_from_artifacts, never contradicted. A checker that cannot decide has learned nothing about the claim. Reporting a contradiction there would turn the checker's own ignorance into evidence against the paper.

Reproducibility statuses

A reproduction re-derives a number from an artifact. Two checks do that: code_execution runs the script, and dataset_statistic recomputes the statistic from the CSV. Reading a value out of a table cell is a lookup, not a reproduction — so a table claim is not_applicable, rather than being inflated into a reproduced result.

StatusMeaningCommitted fixture
reproducedThe recomputed number matched the claim exactly.dataset_mean, recompute_accuracy, gc_content
approximately_reproducedIt landed inside the tolerance, but not on the value.dataset_std
failed_environmentTimed out, exited non-zero, or the sandbox could not enforce its policy.unreproducible_accuracy
failed_missing_dataThe dataset is absent or unusable.none — unit tests only
failed_missing_codeThe script is absent, or its link resolves to nothing.none — unit tests only
failed_numeric_mismatchIt ran, and produced the wrong number.dataset_mean_overstated
not_applicableThe claim exercises no reproduction channel.the five table and passage claims
not_attempted--no-execute, or nothing was declared to compare against.flag only

When a claim exercises both channels, the worst status wins: a script that reproduced does not excuse a dataset that went missing. No committed task has both a script and a dataset, so that rule is pinned by unit tests rather than by a fixture.

The two failed_missing_* statuses have no fixture because they cannot be expressed as one: a task naming an absent fixture file fails to load. They are reachable through the API (a dangling evidence link, a dataset with no path) and pinned by unit tests.

Why failed_environment and failed_numeric_mismatch are separate. Because the checks that feed them are. code_execution judges whether the script ran; a timeout or a non-zero exit is an error, never a fail, since a script that will not run tells you nothing about the claim's number. A separate numeric_tolerance check judges whether the number it printed agrees. A single boolean could not tell these apart. unreproducible_accuracy is the fixture that makes the distinction concrete: its script's input data was never released, so it exits 1, numeric_tolerance is skipped rather than fail — no number disagreed, because no number exists — and the claim keeps whatever support its text gives it. See Checks.

Tolerance

"Within tolerance" above means: within the claim's own reported precision. A value written 3.4 asserts only that the quantity rounds to 3.4, so the threshold is ±0.05; 0.80 gives ±0.005; a count is exact. Every check records the threshold it applied next to the signed difference, and a task or a command-line flag may override it.

The reproducibility sandbox

A script's number is not a result until you know what produced it. Milestone 6 runs every fixture script under a recorded policy, and the policy is the first event in the trace — before the number.

claimverifier run-sandbox --task tasks/code_reproduction/recompute_accuracy.yaml --out results/runs/
ControlMechanismWhat it buys
Fresh working directoryscript copied into an empty temp dir; removed afterit cannot read a repo file it never declared
Scrubbed environmentallowlist: LANG, LC_ALL, LC_CTYPE, PATH, SYSTEMROOTno host token, proxy, or PYTHONPATH reaches the child
Deterministic environmentPYTHONHASHSEED=0, TZ=UTC, no bytecode, no user siteset order, dates, and imports are stable
Wall-clock timeoutparent-side, then killpg(SIGKILL)a script that spawned children does not outlive it
Resource limitsRLIMIT_CPU, RLIMIT_AS, RLIMIT_FSIZE, RLIMIT_NOFILE before execa runaway is stopped by the kernel, not by luck
Network guardin-process socket monkey-patchaccidental network use raises and is recorded
These are reproducibility controls, not security controls. There is no process isolation, no namespace, no seccomp filter. The network guard lives inside the child's own interpreter, so code that means to bypass it can. It catches accidents by trusted fixture code; it does not contain hostile code. See Limitations and docs/SANDBOX.md.

Recording an attempt, not just refusing it

The guard writes the denied call to a log before it raises. A script that catches the exception and carries on still leaves the attempt in network_attempts, so a reproduction that reached for the network cannot look self-contained in the trace. And because site silently swallows exceptions raised from sitecustomize, a guard that failed to install would leave the network open while the trace said blocked — so the bootstrap writes a marker naming the policy it applied, and the runner refuses to return a result without it. The check then reports error, never a verdict about the claim's number: the conditions that number would be attributed to never held.

The trace, and the one value it omits

Two runs of the same script produce byte-identical JSONL. The command is recorded as ("python", "compute_accuracy.py") rather than the machine's interpreter path; the random temp path is replaced with <sandbox> in captured output; file and attempt lists are sorted; the policy record holds no absolute paths.

Wall-clock duration is the exception, and it is opt-in (--with-timing). It is the one fact about an execution that cannot be reproduced, and recording it by default would make every trace differ from every other — the diff between two runs would stop being a signal.

{"data": {"policy": {...}}, "kind": "sandbox.policy", "seq": 0}
{"data": {"command": ["python", "compute_accuracy.py"], "script_hash": "sha256:9bc64b75…"}, "kind": "sandbox.exec", "seq": 1}
{"data": {"stderr": "", "stdout": "accuracy=0.80\n"}, "kind": "sandbox.output", "seq": 2}
{"data": {"exit_code": 0, "network_attempts": [], "ok": true, "timed_out": false}, "kind": "sandbox.result", "seq": 3}

Swapping Milestone 5's bare subprocess.run for this sandbox moved no verdict: the check table stayed 16 pass / 1 fail / 1 inconclusive over the then-seven fixtures. That is the point of having written the check against a runner protocol. (The fixture set is now eleven; see Results.)

Failure modes

A support label says the claim is not backed. A failure mode says what to go and fix. That is what makes an aggregate result diagnostic instead of a pass rate: eight contradicted claims are one number, but "six table-cell mismatches and two paraphrases the lexical checker could not read" is a work list. Every reason is collected; one is chosen by priority, and the rest survive on the result as limitations.

table_cell_mismatch → statistic_mismatch → numeric_out_of_tolerance
  → execution_timeout → execution_error → missing_code → missing_data
  → underspecified
  → passage_does_not_assert → evidence_undecidable → missing_evidence_link → other

Most concrete refutation first; the checker's own reach last. Everything below underspecified is a statement about the checker, not about the paper.

evidence_undecidable vs. passage_does_not_assert. The first says the checker could not tell; the second says the passage does not say it. Milestone 5 introduced the inconclusive check status with no failure mode to map onto, and the nearest existing value asserted something the pipeline does not know — so Milestone 7 added evidence_undecidable (schema 1.2, additive). The synthetic_data_passage passage does assert its claim; a bag-of-words rule simply cannot see it.

The signals a check leaves behind are what make this possible. Given the bare column locator col=accuracy, the table check records matching_rows and n_rows: a claimed value found at one of two rows, with no row named, is underspecified; a claimed value found at no row is contradicted. Same locator, different inputs, different label. And every error check records a closed-vocabulary error_kind, so scoring tells "the script is missing" from "the sandbox broke" by table lookup rather than by matching English in a notes field.

Confidence is decidedness, not probability

VerificationResult.confidence is the share of a claim's checks that reached a pass/fail verdict. It is not calibrated against anything and it is not a probability that the label is correct. A claim whose only check is inconclusive scores 0.00 no matter how confident the wording of its label sounds. Inventing a calibrated number here would need labelled data this project does not have.

Aggregate summary

claimverifier verify --task A --task B … counts support labels, reproducibility statuses, and failure modes across tasks, and compares each to the gold outcome its task file declares. Scoring is deterministic: explanation quality is judged by expected fields, not by an LLM grader.

A single accuracy number would hide the difference between a system that says the wrong thing and one that declines to say anything — and for a verification tool that difference is the whole point. So a mismatch is bucketed:

BucketMeaning
conservative_missesPredicted a non-committal label where gold commits. The system declined to decide; it asserted nothing false.
wrong_verdictsAsserted a committal label the gold outcome disagrees with. These are the mistakes.

Over the committed fixtures wrong_verdicts is 0. It is the number to watch: a change to the extractor, the linker, or the checks that raises label accuracy by turning a conservative miss into a wrong verdict has made the tool worse. See Results.
