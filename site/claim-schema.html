Claim schema

A claim is not free text to be summarized — it is a typed object with explicit, checkable fields. This lets checks target specific values and lets the report separate the claim from the evidence and the inference.

ScientificClaim fields

FieldMeaning

normalized_claimCanonicalized form used for matching.

conditionsStated conditions/qualifiers (split, seed, subset).
expected_valueThe asserted numeric value.

unitsUnits of the value (e.g. %), when stated.
evidence_linksLinks to passages, tables, datasets, or code refs.

Claim types

TypeExamplePrimary check
descriptive_claim"The method is trained on synthetic data."evidence presence
numeric_claim"Accuracy is 78%."numeric tolerance
comparison_claim"A improves accuracy from 72% to 78%."comparison
table_claim"Row B, column F1 is 0.81."table recompute / lookup
figure_claim"The bar for group C is highest."figure/table recompute
dataset_claim"The dataset has 120 samples, mean 3.4."dataset statistic recompute
code_reproduction_claim"Running eval.py yields 0.78."code execution
unsupported_or_contextual_claim"This is the best approach in the literature."flagged as unverifiable / contextual
The canonical, field-by-field definition lives in docs/CLAIM_SCHEMA.md, written to match the pydantic models in schemas.py so the docs and the code cannot drift. Every model forbids unknown fields (extra="forbid"), and the vocabularies below are StrEnums whose values are exactly the strings shown here.

Design intent

  • Every field a check needs is explicit — no re-parsing the claim text at check time.
  • Extraction may be heuristic; the schema is where heuristics are made auditable.
  • An unsupported_or_contextual_claim is a first-class outcome, not an error.
