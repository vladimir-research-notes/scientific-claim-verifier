Integrations

Five versioned export formats, each shaped for a consumer role, each derived from artifacts this repository already produces — and one of them replays.

What this is, and what it is not

No external schema was consulted. None of the five systems these formats are named for was read, imported, or run. This repository therefore cannot claim, and does not claim, compatibility with any of them.

What exists is five proposed contracts, one per consumer role. Each is versioned, validated by a strict reader, and confined to one module of ~200 lines. If a named repo wants different keys, the change is that module and a format_version bump; no pipeline stage knows these formats exist. That containment is the deliverable, and it is checked rather than asserted: a test parses every module under integrations/ and fails if it imports anything but the standard library, pydantic, and this project.

Four properties, held by every format

A function of artifacts

Nothing re-runs the pipeline. The traces are the record, as Milestone 9 established for reports. A test deletes tasks/ and shows three formats are unaffected. replay is the one exception; it exists to re-run.

Deterministic

Canonical JSON — sorted keys, no wall clock, no RNG. Exporting a run twice produces byte-identical files. A non-diffable export is useless to a regression tool.

Portable

Every path is repo-relative; every trace is named by its filename. A test walks every string of every document and fails on an absolute path.

Self-describing

The envelope states the format, the contract version, the producer, and the trace schema. A later major version is refused, not parsed into a plausible-looking object.

The envelope

{
  "format": "scv.benchmark",
  "format_version": "1.0",
  "producer": "scientific-claim-verifier",
  "producer_version": "0.1.0",
  "trace_schema_version": "1.3",
  "payload": { ... }
}

Every payload record is a pydantic model with extra="forbid". An export is a contract, and the two ways a contract rots unnoticed are a consumer silently dropping a field it does not recognise and a producer silently accepting one it never declared. --schema derives the JSON Schema from the very models that write and validate the document, so a published schema cannot drift from the code that honours it.

One vocabulary, shared

Three formats state a verdict. If each spelled it differently, a consumer joining two exports would have to know all five formats to know they agreed. So Verdict lives once — and is never flattened to a single score, in any export:

{"support_label": "contradicted",
 "reproduction_status": "not_applicable",
 "failure_mode": "table_cell_mismatch",
 "confidence": 1.0}

confidence is the share of a claim's checks that reached a verdict — not a probability that the label is right. A gold verdict carries confidence: null, because no pipeline computed it.

scv.runnable-tasks — the trace contract

docs/PLAN.md asks this format to "export traces in a compatible JSONL shape". The trace already is JSONL; what a consumer lacks is a written guarantee about it. The document carries one — and every guarantee is re-derived from a real trace in the tests, because a guarantee nobody checks is a comment.

"guarantees": [
  "one JSON object per line, UTF-8, newline-separated",
  "object keys are sorted within every line",
  "every line carries a contiguous `seq`, starting at 0",
  "every line's `kind` is one of `event_kinds`",
  "no value is read from the wall clock or an RNG",
  "the bytes are identical across re-runs and across output directories"
]

expected.verdict is the task's hand-authored gold outcome: the success criterion a runtime checks, and something that must never be shown to a system asked to solve the task. --hide-gold drops it.

scv.evidence-records — the five channels, as five keys

Not a verdict with a citation stapled to it. An evidence store cannot merge these without noticing:

KeyChannel
claimthe extracted claim, as typed fields
evidencethe supporting text, quoted, with its locator
checkseach computed check: value, expected, tolerance, status
verdictthe inference — three labels wide
unverifiablewhat this verdict does not settle

rules sits beside them: the named inference step behind each verdict field, and the check_ids it read. A store that keeps the rule can answer why does this say contradicted? by lookup. One that keeps only the label cannot.

What is deliberately not exported is VerificationCheck.inputs — the per-check debugging bag whose keys vary by check type and which, for code_execution, holds captured stdout. A stable contract cannot carry a field whose shape is decided by whichever check happened to write it, and an evidence store is the last place that should start holding process output by accident. A test asserts the string accuracy=0.80 — real stdout from a fixture script — appears in no record.

scv.benchmark — the metric is declared, not assumed

A benchmark that ships records without declaring its metric is a spreadsheet. And the metric a harness would reach for by default — label accuracy — is the wrong one here.

{"protocol": "exact_match_per_field",
 "primary_metric": "wrong_verdicts",       "primary_metric_direction": "lower_is_better",
 "secondary_metric": "conservative_misses", "secondary_metric_direction": "lower_is_better",
 "outcomes": ["match", "conservative_miss", "wrong_verdict"]}

Over these fixtures the pipeline recovers 10 of 11 support labels, and its single miss is a claim it declined to decide. A change that "fixed" that miss by guessing would score 11/11 and have made the tool worse. So the primary metric is wrong_verdicts — committal labels the task's own artifacts contradict — and over the committed fixtures it is 0. Do not sum the two. The export computes each task's bucket with the same TaskOutcome object the suite gate reads, not a re-implementation, so the two cannot come to different conclusions.

Predicted verdicts come from the traces; gold, the suite identity, and the gate come from summary.json — a trace never carries gold, because gold is never an input to the run that wrote it. The two are cross-checked, and a directory whose traces and summary disagree is refused, not scored: it holds artifacts from more than one run, and any number computed from it is a fiction.

scv.metrics — a fixed key space

The only property a metrics sink really needs from a producer is the one producers usually get wrong. A run with no contradicted claim could plausibly omit support_contradicted; then a diff against a run with two shows a key appearing, and a tool that reads a missing key as "no data" reports nothing while one that reads it as zero reports a regression. Both are guessing.

So the key space covers every value of every closed vocabulary — 6 support labels, 8 reproduction statuses, 13 failure modes, 5 check statuses — and all 40 metrics are emitted every time, zero-valued when unseen. It changes only when format_version does, and a test enumerates the enums so a vocabulary cannot grow without this format saying so.

direction is the other half: a regression tool cannot know that more checks_fail is fine — a suite of contradicted claims should produce failing checks — while more wrong_verdicts is not. Most counts are neutral; only six declare a direction. A test drives the scenario the whole project is arranged to catch: a conservative miss turning into a wrong verdict, with gold agreement unchanged. Accuracy calls it a wash; compare() flags wrong_verdicts.

scv.episodes — the import direction

The one format where the contract stops being a shape and becomes a claim that can be false. An episode pins the task and its file hash, every artifact of its bundle by content hash, the controls, the recorded verdict, and the SHA-256 of the trace the run wrote.

$ claimverifier replay --episodes episodes.json

Episodes        : 11
Gate            : verdict only

  [ok   ] synthetic_data_passage   reproduced
  [ok   ] negated_training_data    reproduced
  [ok   ] contradicted_f1          reproduced
  ... (8 more)

Reproduced      : 11/11

Result          : PASS
StatusMeaning
reproducedsame inputs, same verdict
driftedsame inputs, different verdict — the pipeline changed
inputs_changeda fixture, a paper, or the task file is not the bytes the episode recorded; no re-run is attempted
missing_taskthe task file is gone

Only drifted is a statement about the pipeline. Collapsing the other three into "failed" would let an edited CSV read as a code regression — precisely the mistake a replay harness exists to prevent. Each of the four is produced by injecting its cause in the tests.

trace_digest_matches is reported for every episode and gated only under --strict: reword one because string and every trace's bytes change while every verdict stands. Over the eleven committed fixtures replay is reproduced 11/11 and passes --strict — the traces come back byte-identical.

An honest gap. A trace records what the pipeline computed, not how an operator invoked it, so a schema-1.3 trace records none of the four controls. execute is recovered from a suite's summary.json and the export refuses when the operator's declared --no-execute disagrees with it; the other three are taken from the operator's flags. A wrongly declared control does not silently lie — replaying it reports drifted and names the field — but it is an assumption, and it is the one this milestone did not remove. Recording the controls in the trace (schema 1.4) would.

Honest limitations

  • No adapter was validated against any of the five named systems. "Compatible" in docs/PLAN.md should be read as "shaped to be compatible with".
  • benchmark, metrics, and episodes need a run-suite run: gold outcomes, a suite identity, and a gate are not in a trace. evidence-records needs only traces and works on an archived run.
  • The fixtures are eleven small synthetic tasks. Every number that leaves here is a fact about this pipeline on those fixtures, not a benchmark result about scientific claim verification.
  • replay runs the fixture scripts, inheriting the sandbox's honest scope: controlled fixture execution, not an untrusted-code boundary. See Reproducibility.
