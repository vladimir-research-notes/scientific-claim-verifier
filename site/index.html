Scientific Claim Verifier

Given a claim and a bundle of scientific artifacts, this system extracts the claim, links it to supporting evidence, runs deterministic checks, attempts lightweight reproduction, classifies failure modes, and produces an auditable report backed by a JSONL trace.

status: Milestone 9 complete — auditable reports, rendered from traces   Milestone 10 next: optional LLM adapters

Why not just summarize?

A summary tells you what a paper says. It does not tell you whether a specific claim is supported by the paper's own artifacts, nor whether the underlying computation reproduces. This project treats a claim as something to be checked through several independent evidence channels, each recorded and inspectable. The output keeps five things visibly separate:

Extracted claim

The normalized claim and its typed fields (metrics, datasets, expected value, operator).

Supporting text

The exact passage(s) linked as evidence, with provenance.

Computed check

A deterministic recomputation, table lookup, or code execution.

Inference

The support label and reproducibility status derived from the checks.

Unverifiable

What could not be checked from the supplied artifacts, and why.

The evidence channels

  1. Does the claim appear in the paper text?
  2. Which exact passage supports it?
  3. Is the claim tied to a table, figure, dataset, or code artifact?
  4. Can the relevant computation be reproduced or approximated from artifacts?
  5. If not, why not (failure mode)?
  6. Is the claim supported, contradicted, partially supported, underspecified, or unverifiable?
  7. Can the system emit a trace a human can audit end to end?

Pipeline

task (YAML/JSON)
  -> artifacts   load + content-hash paper / dataset / code
  -> claims      extract (rule-based / mock LLM) -> normalize
  -> evidence    link passages / tables / datasets / code refs
  -> checks      statistical · table recompute · figure recompute · code execution · consistency
  -> sandbox     temp dir · scrubbed env · timeout · rlimits · network guard · JSONL trace
  -> scoring     support label · reproducibility status · failure mode
  -> report      Markdown (+ optional HTML)  <-  JSONL trace

Running it today

The package (scientific_claim_verifier) and the claimverifier console script are runnable and dependency-light (runtime deps: pydantic, pyyaml). All ten commands are live, and the CLI contract in docs/PLAN.md §10 is complete.

pip install -e .                 # editable install
claimverifier version
claimverifier check-env          # offline interpreter + library self-check
claimverifier validate-fixtures  # validate task and suite fixtures under tasks/
claimverifier extract-claims --task tasks/table_claims/accuracy_improvement.yaml
claimverifier link-evidence  --task tasks/table_claims/accuracy_improvement.yaml
claimverifier run-checks     --task tasks/table_claims/contradicted_f1.yaml
claimverifier run-sandbox    --task tasks/code_reproduction/recompute_accuracy.yaml
claimverifier verify         --task tasks/ml_claims/underspecified_split.yaml
claimverifier run-suite      --out results/runs/   # all 11 tasks, offline, ~1.5 s
claimverifier report         --run results/runs/smoke_suite --out results/reports/
python3 -m pytest -q             # CPU-only, offline tests

Then the checks read each located artifact and compute a fact about it. Here is the fixture that exists to show why the channels must stay separate — a paper whose abstract asserts a claim its own results table refutes:

$ claimverifier run-checks --task tasks/table_claims/contradicted_f1.yaml

Claim : Method B reaches an F1 score of 91.0 on MNLI.

Supporting text (retrieved evidence; whether it *asserts* the claim is checked below):
  "Method B reaches an F1 score of 91.0 on MNLI."

Computed checks (each reads an artifact; none of them decides the verdict):
  [pass] evidence_presence  p_claim         the passage states the claim verbatim
  [fail] table_value        t_mnli[col=f1]  claimed 91 is absent from column 'f1'
                                            (nearest 86 at row B; |difference| = 5 > tolerance 0.05)

Inference : NOT produced by this stage.

Both checks are correct. A system that collapsed them into a single verdict would destroy the only interesting fact about this claim. The 0.05 tolerance was not chosen either — the claim wrote 91.0, to one decimal place, so anything rounding to 91.0 would have matched. See Checks.

Where a claim is about a script, the script runs — under a recorded policy, and the policy is printed before the number, because accuracy=0.80 is not a result until you know what produced it:

$ claimverifier run-sandbox --task tasks/code_reproduction/recompute_accuracy.yaml

Content hash    : sha256:9bc64b75db9d64c24eb78e3696cd5e1679771ac83a74062733d25f65800a3d9a
Command         : python compute_accuracy.py

Policy (recorded verbatim into the trace):
  timeout       : 10.0s
  network       : blocked — in-process socket guard; cooperative, bypassable, not a boundary
  working dir   : fresh temp dir, removed after the run
  env allowlist : LANG, LC_ALL, LC_CTYPE, PATH, SYSTEMROOT
  rlimits       : RLIMIT_AS=2147483648, RLIMIT_CPU=11, RLIMIT_FSIZE=8388608, RLIMIT_NOFILE=256
  isolation     : none — controlled fixture execution, not a security boundary

Outcome         : exited 0
Network attempts: none

stdout:
  accuracy=0.80

The guard records a denied socket call before refusing it, so a script that catches the exception still cannot look self-contained. And the guard's installation is verified rather than assumed — site would otherwise swallow a broken guard and leave the network open while the trace said blocked. See Reproducibility.

Only then does anything draw a conclusion. verify reduces each check to what it says about the claim, applies five ordered rules, and names the rule and the checks it read. Here is the claim the system refuses to decide:

$ claimverifier verify --task tasks/ml_claims/synthetic_data_passage.yaml

Claim : The model is trained only on synthetic data.

Supporting text (retrieved evidence):
  "All experiments use synthetic data generated by our pipeline; no real
   corpora were used at any stage of training."

Computed checks (what each artifact says about the claim):
  [inconclusive] evidence_presence  p_data  -> undecided

Inference (drawn from the checks above; each rule names the checks it read):
  support_label       : unverifiable_from_artifacts
    rule              : nothing_decided [c_synthetic_data.evidence_presence.1]
    because           : a lexical check cannot decide whether the passage asserts
                        the claim (40% token coverage, missing ['model', 'only',
                        'trained'])
  failure_mode        : evidence_undecidable
  confidence          : 0.00 (share of checks that reached a verdict; not a probability)

Task gold       : supported [MISS] / not_applicable [ok ] / none [MISS]

The passage does support the claim — a human reads the paraphrase instantly. A bag-of-words rule cannot, so it says inconclusive, and scoring maps that to unverifiable_from_artifacts, never contradicted. The report marks its own miss. Across the eleven fixtures the pipeline gets 10/11 support labels and 11/11 reproduction statuses, but the number that matters is 0 wrong verdicts: it has never asserted a label the gold outcome disagrees with. Its one miss is a refusal to decide. See Results.

The smoke suite is a gate, not a scoreboard

claimverifier run-suite drives all eleven committed tasks through the whole pipeline — offline, on one core, in about a second and a half — and writes a JSONL trace and a result JSON per task alongside summary.csv, summary.json, and summary.txt. It exits non-zero when the pipeline regresses, and the definition of regression is deliberately asymmetric:

  • Any wrong verdict — a committal support label the task's gold outcome disagrees with — fails the run. The suite file has no key that could declare one acceptable, so it can never bless one.
  • A conservative miss — declining to decide where the gold outcome commits — fails the run only if the set of them changed. The suite file names the standing misses; a new one is a regression, and a fixed one must be removed rather than left to rot.

That asymmetry is the whole point. A change that raises label accuracy by turning a claim the pipeline honestly declined to decide into one it decides wrongly has made the tool worse, and a single accuracy number would have called it an improvement. A suite full of contradicted claims exits 0 — finding a contradiction is the tool working.

$ claimverifier run-suite --out results/runs/

Suite : smoke_suite (Offline smoke suite) v1    Tasks : 11

  [shy ] synthetic_data_passage   unverifiable_from_artifacts / not_applicable / evidence_undecidable
         gold: supported / not_applicable / none
  [ok  ] negated_training_data    contradicted / not_applicable / passage_does_not_assert
  [ok  ] contradicted_f1          contradicted / not_applicable / table_cell_mismatch
  [ok  ] underspecified_split     underspecified / not_applicable / underspecified
  [ok  ] dataset_std              supported / approximately_reproduced / none
  [ok  ] dataset_mean_overstated  contradicted / failed_numeric_mismatch / statistic_mismatch
  [ok  ] unreproducible_accuracy  partially_supported / failed_environment / execution_error
  ... (4 more)

Wrong verdicts      : 0
Conservative misses : 1 ['synthetic_data_passage']

Gate            : PASS

The gate is tested by injecting each failure in turn — a wrong verdict, a new conservative miss, a stale declared miss — and asserting it rejects the run. A gate that never fails proves nothing when it passes.

The report is a function of the trace

claimverifier report renders each claim as Markdown (or standalone HTML) with the five channels in numbered sections — extracted claim, supporting text, computed check, inference, unverifiable — plus a link to the JSONL trace it came from. It does not import the extractor, the linker, the checks, or the sandbox. It reads one <task_id>.trace.jsonl and reconstructs the scored claim from it, re-validating every object against the schema on the way in, so a corrupt trace raises rather than rendering into a plausible-looking report.

$ claimverifier report --run results/runs/smoke_suite --out results/reports/
wrote 12 file(s) for 11 claim(s) from results/runs/smoke_suite

A run archived months ago, whose papers and CSVs are long gone, still reports. That is a claim worth testing rather than asserting, so a test scores every committed fixture, writes its trace, reads it back, and asserts the reconstruction equals the original result, rules, and signals. A trace that cannot be turned back into the verdict it recorded is not an audit record — it is a log. See the Example report.

Tests import the package straight from src/ (no install required) and never touch the network. See Milestones for what each build step adds.

Constraints

  • CPU-only, offline, and free by default. Target hardware: AWS m5.2xlarge. No GPU.
  • No paid API in the default path. Optional LLM adapters are disabled by default and, if enabled, require dry-run, a response cache, a token/cost estimator, a hard max-cost guard, and explicit opt-in.
  • Fixtures are small, synthetic or open, and committed. Tests never touch the network.

What this is not

Not a paper summarizer, not a learning demo, and not an oracle of scientific truth. Verdicts are relative to the supplied artifacts. The system is explicitly out of scope for clinical decisions, medical advice, and wet-lab protocols — see Safety.
